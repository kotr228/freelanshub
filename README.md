# Freelanshub

Біржа фрілансу: замовники публікують замовлення, фрілансери беруть їх у роботу, спілкуються в чаті, обмінюються файлами, а оплата проходить лише після виконання.

Стек: **Next.js 16 (App Router, Server Actions)**, React 19, TypeScript, Tailwind CSS 4, **PostgreSQL (Neon) + Prisma 7**, сесії в підписаному cookie (`jose`), паролі — bcrypt.

## Можливості

- Реєстрація та вхід для двох ролей: замовник і фрілансер.
- **Замовник:** публікує замовлення (тип, спеціальність, дедлайн, бюджет, файли) з розрахунком комісії; бачить вкладки «Активні / Вільні / На виконанні / Очікують оплату / Завершені»; скасовує вільне замовлення; сплачує виконане; архівує сплачене.
- **Фрілансер:** каталог вільних замовлень з фільтрами (пошук, спеціальність, тип, дедлайн, ціна, сортування) і пагінацією; ставить запитання до того, як взятися; бере замовлення, відмовляється від нього або позначає виконаним; вказує картку для виплат.
- Чат у кожному замовленні (окремий діалог для кожного фрілансера) з вкладеннями, файли замовлення, сповіщення про ключові події.
- **Відгуки й рейтинг:** після оплати сторони оцінюють одна одну (1–5 ★), середня оцінка видна на сторінці замовлення.
- Налаштування профілю: ім'я, контакти, «про себе», аватар, пошта, зміна пароля, банківська картка.
- Щоденне автоочищення старих замовлень та їхніх файлів (`/api/cron/cleanup`).

Життєвий цикл замовлення (`Job.status`): `OPEN` — вільне → `IN_PROGRESS` — в роботі → `DONE` — виконане, чекає оплату → `PAID` — сплачене → `ARCHIVED`.

## Запуск

Потрібен Node.js 22+.

```bash
cp .env.example .env      # DATABASE_URL, DIRECT_URL (Neon), SESSION_SECRET, CRON_SECRET
npm install               # postinstall запускає prisma generate
npm run db:deploy         # застосовує міграції з prisma/migrations до бази
npm run dev               # http://localhost:3000
```

Продакшн: `npm run db:deploy && npm run build && npm run start`.

### Якщо `npm run dev` показує «An unexpected Turbopack error occurred»

1. Подивіться вивід у терміналі, де запущено `npm run dev`: там є справжня причина і шлях до `next-panic-*.log`.
2. Після `git pull` виконайте `npm install` (генерує Prisma Client у `src/generated/prisma`), потім видаліть кеш: `rm -rf .next` (Windows PowerShell: `Remove-Item -Recurse -Force .next`).
3. Запасний варіант без Turbopack: `npm run dev:webpack`.

### База даних

- Схема — `prisma/schema.prisma`, міграції — `prisma/migrations`, клієнт — `src/lib/prisma.ts`.
- `DATABASE_URL` — пулований рядок Neon (хост з `-pooler`), його використовує застосунок.
  `DIRECT_URL` — прямий рядок без `-pooler`, його використовує Prisma CLI для міграцій (див. `prisma.config.ts`).
- Для Neon клієнт працює через `@prisma/adapter-neon`, для будь-якого іншого PostgreSQL (локальний, Docker, CI) — через `@prisma/adapter-pg`, тож розробляти можна і без Neon.
- Змінили схему → `npm run db:migrate -- --name опис_змін` (створює і застосовує нову міграцію).
- `npm run db:studio` — перегляд і редагування даних.

### Автоочищення

Раз на добу викликайте:

```bash
curl -H "Authorization: Bearer $CRON_SECRET" https://your-host/api/cron/cleanup
```

Видаляє вільні замовлення, дедлайн яких минув понад 30 днів тому, і завершені замовлення, старші за рік, разом із файлами. Записи про оплати зберігаються.

## Структура

```
prisma/                  schema.prisma і SQL-міграції
src/app/                 сторінки (App Router)
  (auth)/                вхід і реєстрація
  (app)/client           кабінет замовника
  (app)/freelancer       каталог і замовлення фрілансера
  (app)/orders/[id]      сторінка замовлення: дії, файли, чат, відгуки
  (app)/settings         налаштування акаунта
  actions/               Server Actions: auth, jobs (створення і списки), orders (дії із замовленням), settings
  api/                   чат, завантаження файлів, аватари, сповіщення, cron
src/lib/                 Prisma-клієнт, сесії, запити, валідація, константи
src/generated/prisma     згенерований Prisma Client (не в git)
src/components/          UI-компоненти
storage/                 завантажені файли (не в git, віддаються з перевіркою доступу)
```

## Безпека

- Доступ до замовлень, файлів і чату перевіряється на сервері. Зміни статусу атомарні (умовний `updateMany`), тож двоє фрілансерів не візьмуть одне замовлення.
- Обмеження в самій БД: оцінка 1–5, ціна > 0, не можна оцінити самого себе, один відгук на замовлення від кожної сторони.
- Файли зберігаються поза `public/` і віддаються як `attachment`, тож завантажений HTML/SVG не виконається на сайті.
- Облікові дані — лише в змінних середовища.

> ⚠️ Пароль до старої MySQL-бази був закомічений у PHP-версії й лишається в історії git. Якщо та база ще працює — змініть пароль.

Оплата наразі імітується (`payOrder` у `src/app/actions/orders.ts` записує платіж у таблицю `payments`); для реальних платежів туди треба підключити платіжного провайдера.

Завантажені файли зберігаються на диску сервера (`STORAGE_DIR`). На serverless-хостингу (Vercel тощо) диск не постійний — там `src/lib/storage.ts` треба перевести на об'єктне сховище (S3, Cloudflare R2, Vercel Blob).
